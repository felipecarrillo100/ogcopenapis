# OGC API Features write support

Research and feasibility report for adding create, replace, update and delete to `OgcOpenApiFeatureStore`. Date: 2026-11-09.

Sources: the research notes in `research_notes/OGC API Features write support/` (Part 4 spec, Part 11, write capability discovery, server implementations, LuciadRIA Store API) and the spikes in `spikes/` (pygeoapi, ldproxy, QGIS Server, GeoServer, each on its own PostGIS, plus a browser CORS spike). Every server behaviour below was observed against our own containers and checked in the database, unless it says otherwise.

## 1. Summary

- **Feasible.** OGC API Features Part 4 maps cleanly onto LuciadRIA's `add`, `put` and `remove`. Two of our test servers (ldproxy 4.8.2 and pygeoapi 0.24.0) create, replace and delete features correctly enough to test against, and ldproxy also supports standard PATCH.
- **No standard way to know in advance whether *this user* may write.** Conformance is server-wide, OpenAPI is optional and the same for everyone on 3 of 4 servers, and `OPTIONS`/`Allow` is per user only on QGIS. The answer to the write itself is the only reliable signal.
- **Servers disagree on almost everything around the core operations:** denied-write status codes (400, 401, 403, 500), PUT semantics (replace or merge), `Content-Crs`, locking, error bodies. The client must report what the server said and not interpret it.
- **Batch and transactions are out.** Part 11 exists only as a proposal and no test server implements it.
- **Scope rule:** we implement only what we can test against our own servers.

## 2. The standards

| Document | Status (2026-11-09) | Relevance |
|---|---|---|
| Features Part 1 Core, Part 2 CRS, Part 3 Filtering | Approved | The store reads with these today |
| **Part 4 Create, Replace, Update, Delete** (20-002r2, 1.0.0-draft.3, 2026-09-21; also published as OGC API Common Part 5) | **Draft**, past public comment, prepared for submission to the TC | The basis of this work |
| Part 5 Schemas (23-058r2) | Approved 2026-04-30 | `/collections/{id}/schema`: property types, geometry type, `readOnly` |
| **Part 11 Atomic and Batch Transactions** (26-018) | **Proposal only**; the draft says it is not an OGC standard and its own conformance URIs are inconsistent | Out of scope |

Part 4 in short:
- **Create:** `POST /collections/{c}/items` with `application/geo+json`; 201 + `Location` (or 202). The server assigns the id.
- **Replace:** `PUT /collections/{c}/items/{id}`; 200 or 204. PUT to a missing id creates only where the collection says `supportsNonAutogeneratedResourceIds: true`.
- **Update:** `PATCH` with `application/merge-patch+json` (RFC 7396); `null` removes a property.
- **Delete:** `DELETE`; 200 or 204, 404 for a missing feature.
- **Discovery:** `OPTIONS` is mandatory on every resource, `Allow` lists the methods allowed "in the context of the request", with `Accept-Post`/`Accept-Patch`.
- **Locking:** optional, either ETag + `If-Match` or `Last-Modified` + `If-Unmodified-Since`; 412 on failure.
- **CRS:** CRS84 by default; with Part 2 the client declares another CRS with `Content-Crs: <uri>`.
- **Security:** informative only. 401 + `WWW-Authenticate` without credentials, 403 without rights, 404 allowed to hide resources.
- **Batch:** deliberately excluded (issue #942); left to Part 11.
- **Conformance URIs moved between drafts:** `ogcapi-features-4/1.0/conf/...` (draft.2) and `ogcapi-common-5/1.0/conf/...` (draft.3). ldproxy declares `ogcapi-features-4/0.0/...`. A client must accept all of them.

## 3. Can this user write here? Discovery mechanisms compared

| Mechanism | Scope | What we observed |
|---|---|---|
| `/conformance` | Server only | Says the software *can* write, never that you may. pygeoapi declares it even with nothing editable. QGIS 4.2.3 writes without declaring it. GeoServer correctly declares nothing. |
| OpenAPI (`/api`) | Per collection, optionally per user | Per user only on QGIS. ldproxy lists writes even on a collection with CRUD disabled. `securitySchemes` only on ldproxy. |
| `OPTIONS` + `Allow` | Per resource, per user (by the draft) | Per user only on QGIS. pygeoapi: per collection, the same for everyone. ldproxy: per path template only, and not readable from a browser (not exposed). GeoServer: lists all methods, which then fail with 500. |
| CORS preflight `Access-Control-Allow-Methods` | none | Static on every server; a preflight never carries credentials. Not a permission signal. |
| Collection metadata | – | No editability flag (rejected by the SWG, issue #505). Only `supportsNonAutogeneratedResourceIds` (PUT-create). |
| `/schema` | Per property | `readOnly` on ldproxy's `id` only. No server lists `required`. |
| **The write's response** | Per request | **The only authoritative answer.** But see §5: the status codes differ per server. |

Probing with a fake write is not safe: a server that ignores `If-Match` (all three write servers do) performs the destructive write.

Roles:
- **ldproxy:** reference write server; the only one for PATCH and `Content-Crs`.
- **pygeoapi:** second write server for create, replace and delete; known deviations exercise error reporting.

## 5. Findings that shape the design

### 5.1 LuciadRIA (2026.1.1)
- `Store` is an abstract class; `add`, `put`, `remove` throw unless overridden and reported by `isOperationSupported`.
- `FeatureLayer` reads `isOperationSupported` once; editing needs all three of add, put and remove. **So supported operations must be known when the store is constructed.**
- `add(feature)` must resolve to the server id and emit `StoreChanged` `"add"` with that id; `put` emits `"update"`; `remove(id)` emits `"remove"` (no options parameter, so no precondition can be passed).
- The WorkingSet waits **10 s** for that event; a slower server makes the edit fail on the map even if it succeeds later.
- `get` must resolve `undefined` for a missing feature. **Ours resolves `null` today** ([src/OgcOpenApiFeatureStore.ts:166](../src/OgcOpenApiFeatureStore.ts)).
- No PATCH, ETag or batch concept.
- LuciadRIA 2026.1 `WFSFeatureStore` does WFS-T and sets `isOperationSupported` from the advertised `Transaction` operation: the same pattern of fixing capabilities at creation.

### 5.2 MapEvolution (hackaton) and its WFS-T integration
- Uses LuciadRIA's own `WFSFeatureStore`; edits go to the server immediately, no queue.
- The UI rolls back a rejected edit and records undo only after the server accepts. Undoing a delete re-inserts with `add` and follows the **new** server id.
- Its error classifier already reads `OgcOpenApiError.status`.
- Batch and locking are parked behind a separate session object, not a queuing store.

### 5.3 Browser behaviour (Chromium 151, Chrome 157, WebKit 26.6)
- **`credentials: "include"` fails** with a bare `TypeError` against ldproxy (`*` + credentials), GeoServer (`*`) and pygeoapi's own CORS (no `Allow-Credentials`). LuciadRIA's `credentials: true` becomes `include`. An explicit `Authorization` header with `omit`/`same-origin` works on every server, Bearer included.
- Our `OgcOpenApiFetchTools` works for writes; credentials stay limited to the server's own origin.
- `Location` is readable after POST on every write server; the id is the last path segment.
- `Allow` is readable on pygeoapi and QGIS only; `WWW-Authenticate` only through our nginx proxies.
- **ldproxy marks features `Cache-Control: public, max-age=31536000, immutable`, and Chrome serves the old feature after a successful PUT, PATCH or DELETE** (even 200 for a deleted one). `cache: "no-cache"` avoids it.
- A 401 with an explicit header resolves at once. A possible native login dialog was seen only with `include` in visible Chrome (not verified).

### 5.4 Feature description
- `/collections/{id}/schema` (Part 5) describes every property's type and the geometry type. Queryables are a subset (ldproxy's are empty) and must not substitute for it: on ldproxy a PUT built from a subset sets the missing properties to NULL in the database.
- Available on ldproxy and pygeoapi only.

|---|---|---|

| 2 | Test servers: ldproxy, pygeoapi (writes), QGIS Server (discovery), GeoServer (read-only), newest official releases | user |
| 3 | Batch and transactions out (including ldproxy's FeatureCollection POST); revisit if a test server gains them | user |

## 7. Risks and limits

- **Part 4 is a draft.** Conformance URIs and details may change on approval.
- **Lost updates.** No locking: concurrent edits silently overwrite each other on every server.
- **2xx does not mean "saved as sent"**: pygeoapi PUT merges and trusts the body id; QGIS drops geometry; ldproxy drops unknown properties. We report, not repair.
- **ldproxy collections configured to require `If-Unmodified-Since`** reject our writes with 400; reported as an error.
- **Status codes cannot be mapped to one meaning across servers** (401 on ldproxy covers "not allowed"; QGIS uses 403 for "log in").
- **10 s WorkingSet timeout** in LuciadRIA for edits through the map controllers.
- **Unreleased server fixes** (ldproxy 4.9: 428, `If-Match`, `Prefer`; QGIS 4.4: Part 4 conformance) will change observed behaviour; recorded fixtures must be refreshed when we move to them.
- **Firefox untested** (no build available locally).
