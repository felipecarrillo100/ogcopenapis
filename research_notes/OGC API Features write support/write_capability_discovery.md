# Discovering write capability (CREATE/REPLACE/UPDATE/DELETE) per server, per collection and per user in OGC API - Features

Scope note: "Part 4" below is *OGC API - Features - Part 4 / OGC API - Common - Part 5: Create, Replace, Update and Delete*. Two texts exist and differ: the published editor's draft **1.0.0-draft.2** at https://docs.ogc.org/DRAFTS/20-002r1.html, and the GitHub master source **1.0.0-draft.3** (last commit 2026-10-05) at https://github.com/opengeospatial/ogcapi-features/tree/master/extensions/transactions/create-replace-update-delete/standard. Part 4 is still a draft, not an approved OGC Standard. Where they differ, draft.3 is quoted and the difference is noted. "Standardized" means a normative Part 4 / Part 1 / RFC / Fetch provision. "Heuristic" means anything else.

## 1. Conformance declaration (/conformance): which URIs signal write support, scope, per-user variation

### Takeaway
The conformance declaration only tells a client that the server implements the Part 4 mechanics somewhere. It is server-wide, has no per-collection granularity and no per-user semantics, and the URIs are still in flux across drafts and implementations. Treat it as a capability hint ("this server may have mutable resources") and never as proof that a given user can write to a given collection.

### Cited Findings
- Draft.2 conformance class URIs: `http://www.opengis.net/spec/ogcapi-features-4/1.0/conf/create-replace-delete`, `.../conf/update`, `.../conf/features`. In Table 2 the optimistic-locking classes are printed with `/req/` instead of `/conf/` (`.../1.0/req/optimistic-locking-timestamps`, `.../1.0/req/optimistic-locking-etags`). That is an internal inconsistency in the published draft. — [Part 4 draft.2](https://docs.ogc.org/DRAFTS/20-002r1.html)
- Draft.3 (co-branded with Common Part 5) templates the generic classes as `http://www.opengis.net/spec/{standard}/{m_n}/conf/create-replace-delete`, `/conf/update`, `/conf/optimistic-locking-timestamps`, `/conf/optimistic-locking-etags`, `/conf/return-resource-representation-in-response` and `/conf/handling`. Only `http://www.opengis.net/spec/ogcapi-features-4/1.0/conf/features` is concrete. Seven conformance classes. — [clause_2_conformance.adoc (draft.3)](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_2_conformance.adoc)
- ldproxy (master, 2026-11-06) declares the generic classes under the **Common Part 5** prefix: `http://www.opengis.net/spec/ogcapi-common-5/1.0/conf/create-replace-delete`, `.../conf/update`, plus `http://www.opengis.net/spec/ogcapi-features-4/1.0/conf/features`. The code comments "The draft is co-branded, the conformance classes that are not specific to features are identified by the URIs of OGC API - Common - Part 5." It adds optimistic-locking-timestamps, handling and similar classes only if *any* collection is configured for them. — [ldproxy EndpointCrud.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-draft/ogcapi-crud/src/main/java/de/ii/ogcapi/crud/app/EndpointCrud.java)
- pygeoapi (master, 2026-11-06) hardcodes `http://www.opengis.net/spec/ogcapi-features-4/1.0/conf/create-replace-delete` in `CONFORMANCE_CLASSES_FEATURES`. It adds that list to /conformance whenever *any* `feature` provider exists, whether or not any collection has `editable: true`. — [pygeoapi api/itemtypes.py L78-92](https://github.com/geopython/pygeoapi/blob/master/pygeoapi/api/itemtypes.py), [pygeoapi api/__init__.py ~L880-890](https://github.com/geopython/pygeoapi/blob/master/pygeoapi/api/__init__.py)
- STAC uses its own class `https://api.stacspec.org/v1.0.0/ogcapi-features/extensions/transaction`. Its maintainer states that it "can detect whether a server generally supports transactions" but not "whether the user ... has permission". — [stac-api-extensions/transaction#15](https://github.com/stac-api-extensions/transaction/issues/15)
- Issue #1005 lists "Send Authentication header to the /conformance endpoint and only return the transaction conformance class when the user has permission" as one *possible* option. The SWG answer pointed to OPTIONS instead, and the issue was closed 2026-09-02 via PR #1076, which adds CORS/OPTIONS text. A per-user conformance declaration was not adopted. — [ogcapi-features#1005](https://github.com/opengeospatial/ogcapi-features/issues/1005), [PR #1076](https://github.com/opengeospatial/ogcapi-features/pull/1076)
- Part 1 describes the conformance declaration as stating "the conformance classes ... that the API conforms to. Clients can but are not required to use this information." — [Part 1 master clause_7_core.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/core/standard/clause_7_core.adoc)
- The Part 4 ATS test `/conf/{conf-class}/options` has "Condition: none, the test is executed for every Web API under test". It takes "the list of mutable resources (test parameter)". So conformance is about the existence of mutable resources, and the tester supplies which ones. — [annex_ats_create-replace-delete.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/annex_ats_create-replace-delete.adoc)

### Inferences
- A client should accept at least three URI families as equivalent signals of CRD support: `ogcapi-features-4/1.0/conf/create-replace-delete`, `ogcapi-common-5/1.0/conf/create-replace-delete`, and the STAC transaction URI. For UPDATE the families are `.../conf/update` under features-4 and common-5. The client should also report the draft.2 `/req/` versus `/conf/` mix-up for the locking classes rather than silently normalizing it.
- Absence of the class is a reasonably strong "read-only server" signal for a conformant server. Presence says nothing per collection: pygeoapi declares it with zero editable collections. The client should report "conformance claims CRD but no resource advertises POST/PUT/PATCH/DELETE in Allow" as a server inconsistency, not as an error.
- Nothing in Part 1 or Part 4 says /conformance may vary by user. A server doing so would be legal under HTTP but non-standard. A client must not rely on it, and must send `Vary`-aware requests if it ever compares anonymous and authenticated responses.

### Gaps
- No final, approved conformance URIs exist (draft status). Which prefix the approved standard will use for the generic classes (features-4 or common-5) could not be confirmed.
- I found no evidence of any server that varies /conformance by authenticated user.

## 2. OpenAPI definition (/api): per-collection paths, write operations, securitySchemes, per-user variation

### Takeaway
The OpenAPI definition can list POST/PUT/PATCH/DELETE per path and declare which auth schemes each operation accepts. Part 4 says the API definition "must reflect" what the user can modify. Part 1, however, explicitly allows a single parameterized `{collectionId}` path, OpenAPI security requirements describe *authentication*, not *authorization*, and per-user variation of /api is permitted but not required. It is a medium-reliability, heavy-weight source.

### Cited Findings
- Part 1 allows two approaches: "One approach is to use a path parameter `collectionId`, i.e., the API definition has only a single path entry for all feature collections. Another approach is to explicitly define each feature collection in a separate path ... Both approaches are valid." — [Part 1 master clause_9_oas.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/core/standard/clause_9_oas.adoc)
- `/req/oas/oas-impl`: "The server SHALL implement all capabilities specified in the OpenAPI definition." `/req/oas/completeness`: the definition "SHALL specify for each operation all HTTP Status Codes and Response Objects that the server uses in responses". These are /req/oas30/... in the published 1.0 text. Part 1 also notes that "servers that, for example, are access-controlled ... will make use of additional HTTP status codes" and "Clients have to be prepared to receive responses not documented in the OpenAPI definition." — [Part 1 master requirements/oas](https://github.com/opengeospatial/ogcapi-features/tree/master/core/standard/requirements/oas), [clause_9_oas.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/core/standard/clause_9_oas.adoc)
- Part 4 Security Considerations (draft.3) says users who modify resources need to "1. Be authenticated, 2. Have 'modification privileges' on one or more of the resource collections ..., 3. Have access to one or more of the POST, PUT, PATCH and/or DELETE methods". It continues: "The API definition must reflect this in the resource paths and their available methods." This is informative text, not a numbered requirement. — [clause_13_security_considerations.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_13_security_considerations.adoc)
- The same clause says: "The OpenAPI definition will declare the authentication schemes that the server supports for each operation ... A member 'security' in the OpenAPI definition object can be provided to list the default security schemes ... Individual operations can override this default." Its example says "The server will decide, if an authenticated request is rejected or executed based on privileges of the authenticated user." — [clause_13 (draft.3)](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_13_security_considerations.adoc)
- OpenAPI 3.1: "When a list of Security Requirement Objects is defined on the OpenAPI Object or Operation Object, only one of the Security Requirement Objects in the list needs to be satisfied to authorize the request." "To make security optional, an empty security requirement ({}) can be included in the array." "The Paths MAY be empty, due to Access Control List (ACL) constraints." — [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0.html)
- SWG discussion (issue #135): the server could serve a generic /api with `{collectionId}` to anonymous users, and "a user that is logged in could also get an OpenAPI definition at `/api` with the explicit collection list". This was never made normative. — [ogcapi-features#135](https://github.com/opengeospatial/ogcapi-features/issues/135)
- CubeWerx reports that its OpenAPI document "also lists the HTTP methods available at each endpoint, and that too is sensitive to identity". It also calls it "a rather heavyweight thing for a client to look up". — [ogcapi-common#179 comment by pomakis](https://github.com/opengeospatial/ogcapi-common/issues/179)
- pygeoapi generates per-collection paths and adds `post` (items) and `put`/`delete` (item) only "if p.editable". That is configuration-based, not user-based, since pygeoapi has no built-in auth. — [pygeoapi itemtypes.py ~L1202, ~L1367](https://github.com/geopython/pygeoapi/blob/master/pygeoapi/api/itemtypes.py), [pygeoapi transactions docs](https://docs.pygeoapi.io/en/latest/transactions.html)
- ldproxy builds POST/PUT/PATCH/DELETE operations per collection only for collections whose provider supports mutations (`isEnabledForApi(apiData, collectionId)`). Its access control (`data:write` permission group, per-collection suffixes like `data:getItems::daraa:AeronauticSrf`, OAuth scopes) is described separately in server config. — [EndpointCrud.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-draft/ogcapi-crud/src/main/java/de/ii/ogcapi/crud/app/EndpointCrud.java), [ApiSecurity.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-stable/ogcapi-foundation/src/main/java/de/ii/ogcapi/foundation/domain/ApiSecurity.java)
- STAC discussion: reading OpenAPI is "heavy and rather complex (at least from a web UI perspective)" and can be "like a megabyte". OAuth `scopes` exist only for `oauth2`/OIDC schemes, and "I'm also not sure how the scopes would tell me whether a user has access or not unless we define a common set of scopes". — [stac-api-extensions/transaction#15](https://github.com/stac-api-extensions/transaction/issues/15)

### Inferences
- If a collection-specific path exists and lacks `post`/`put`/`patch`/`delete`, that is a fairly strong "not mutable (by configuration)" signal, because `/req/oas/oas-impl` binds the server to what it documents. The converse is weak: a parameterized `/collections/{collectionId}/items` with `post` means only that *some* collection may accept POST.
- An operation-level `security` requirement means "this operation needs credentials of scheme X". It never means "the current user is authorized". An empty `{}` entry or no `security` means anonymous calls are possible in principle, not that they will succeed.
- Per-user OpenAPI is permitted (issue #135 discussion, CubeWerx), but a client can't tell whether a given /api is user-tailored. Comparing anonymous and authenticated /api responses is possible but expensive, and caches (no `Vary: Authorization`) can confuse it.

### Gaps
- No normative Part 4 requirement on the OpenAPI content for mutation operations (e.g. /req/oas30/... for POST) was found in draft.2 or draft.3.
- Whether ldproxy filters its OpenAPI per user could not be confirmed from the sources read.

## 3. HTTP OPTIONS and the Allow header

### Takeaway
OPTIONS with `Allow` is **the** standardized Part 4 discovery mechanism, and the only one that is normatively per-resource and per-request-context ("at the time and within the context of the request"). Real implementations currently compute it from configuration, not from the authenticated user, and browser/CORS constraints limit what a cross-origin web client can read. It is the best signal, but advisory.

### Cited Findings
- `/req/core/methods` A: "A server SHALL implement one or more of the methods HTTP POST, PUT and/or DELETE for each mutable resource." B: "A server SHALL declare which methods are supported for each resource via the HTTP OPTIONS method." The text right after: "Note that the POST, PUT and/or DELETE methods will typically only be available for authorized users with sufficient permissions. The methods available to a user are available via the OPTIONS method for each resource." — [REQ_methods.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/create-replace-delete/REQ_methods.adoc), [clause_6 (draft.3)](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_6_create-replace-delete.adoc)
- `/req/create-replace-delete/options-op` A: "The server SHALL support the HTTP OPTIONS operation at each resource endpoint." `/req/create-replace-delete/options-response`: A, 200 on success; B, "A response with HTTP status code `200` SHALL include an `Allow` header"; C, "The value of the `Allow` header SHALL be the list of methods that are allowed for the resource at the time and within the context of the request." — [options/REQ_op.adoc, REQ_response.adoc](https://github.com/opengeospatial/ogcapi-features/tree/master/extensions/transactions/create-replace-update-delete/standard/requirements/create-replace-delete/options)
- `/req/create-replace-delete/options-accept-post` (condition: Allow includes POST): the response "SHALL include an `Accept-Post` header ... with the media types that the server supports" for CREATE. `/req/update/methods`: "A server SHALL declare support for the HTTP PATCH method via the HTTP OPTIONS method." There is also `/req/update/accept-patch`. — [REQ_accept-post.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/create-replace-delete/options/REQ_accept-post.adoc), [requirements/update](https://github.com/opengeospatial/ogcapi-features/tree/master/extensions/transactions/create-replace-update-delete/standard/requirements/update)
- The POST/PUT/DELETE operation requirements are conditional on OPTIONS. For example, `/req/create-replace-delete/delete-op` has "Condition: Server declares support for the DELETE method on the resources endpoint via the `Allow` header in the response to an OPTIONS request." — [delete/REQ_delete-op.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/create-replace-delete/delete/REQ_delete-op.adoc)
- `/per/options/other-methods`: GET, HEAD and so on MAY also be listed. `/per/create-replace-delete/options/res-body`: the OPTIONS response body "MAY include content but the format ... is not defined". — [recommendations/create-replace-delete/options](https://github.com/opengeospatial/ogcapi-features/tree/master/extensions/transactions/create-replace-update-delete/standard/recommendations/create-replace-delete/options)
- Draft.3 adds informative "HTTP Link Hints". An OPTIONS body may carry a `self` link with hints `allow`, `accept-post`, `accept-patch`, `formats`, `precondition-req` (`etag`/`last-modified`), `accept-prefer` and `auth-schemes`. "Link hints are advisory ... the behavior of the resource at the time of the request always overrides the hinted information." It is based on [draft-ietf-httpapi-link-hint](https://www.ietf.org/archive/id/draft-ietf-httpapi-link-hint-02.html), and nothing is normative until that becomes an RFC. — [clause_6 (draft.3) "HTTP Link Hints"](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_6_create-replace-delete.adoc), [ogcapi-features#505](https://github.com/opengeospatial/ogcapi-features/issues/505)
- ATS `/conf/{conf-class}/options` asserts 200, an `Allow` header listing at least one of POST/PUT/PATCH/DELETE, and `Accept-Post` when POST is allowed. Later CREATE/REPLACE/DELETE tests run only on endpoints whose `Allow` lists the method. — [annex_ats_create-replace-delete.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/annex_ats_create-replace-delete.adoc)
- Open issue #1058 (2026-07-16) proposes rewording Req 1 B to "allowed for the resource (and authorized in this context)". This shows the per-user reading is intended but not yet explicit in Req 1. — [ogcapi-features#1058](https://github.com/opengeospatial/ogcapi-features/issues/1058)
- RFC 9110 §9.3.7: OPTIONS "allows a client to determine the options and/or requirements associated with a resource ... without implying a resource action". A server "SHOULD send any header that might indicate optional features ... (e.g., Allow)". §9.2.1 lists OPTIONS among the safe methods. §10.2.1: Allow "lists the set of methods advertised as supported by the target resource ... The actual set of allowed methods is defined by the origin server at the time of each request." — [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-options)
- Part 1: "Servers implementing CORS will implement the method OPTIONS, too." Part 1 itself does not require OPTIONS. — [Part 1 clause_7_core.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/core/standard/clause_7_core.adoc)
- CubeWerx: its OPTIONS `Allow` "is sensitive to identity as well, so clients will get an 'Allow' response header that's specific to them based on the access-control rules of the server". — [ogcapi-common#179](https://github.com/opengeospatial/ogcapi-common/issues/179)
- **ldproxy OPTIONS is not user-specific.** The handler takes `@Auth Optional<User> optionalUser` but never uses it. It computes `Allow` from the endpoints configured for the path and returns the *same* response as the CORS preflight answer: `Allow`, `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods` (same list), `Access-Control-Allow-Headers` (including Authorization), `Accept-Post` and `Accept-Patch`. The body is `text/plain` with the method list. It sends no `Access-Control-Allow-Credentials` and no `Access-Control-Expose-Headers`. — [ldproxy OptionsEndpoint.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-stable/ogcapi-foundation/src/main/java/de/ii/ogcapi/foundation/infra/rest/OptionsEndpoint.java)
- **pygeoapi OPTIONS is configuration-based.** `Allow: HEAD, GET` gets `, POST` (items) or `, PUT, DELETE` (item) only `if p.editable`. PATCH is never listed. There is no user context. — [pygeoapi itemtypes.py ~L780-787](https://github.com/geopython/pygeoapi/blob/master/pygeoapi/api/itemtypes.py)

### Inferences
- Reliability ranking: OPTIONS/Allow is the most specific standardized signal (per resource, per request context). In practice today it is usually "per resource, per configuration". A client should use it as "the server says method M is possible here" and still treat a subsequent 401/403 as authoritative.
- A client should send OPTIONS *with the same credentials* it will use for the write: Authorization header or credentials mode `include`. Otherwise it gets the anonymous view at best.
- PATCH missing from Allow while the server claims the `update` conformance class is a reportable inconsistency (pygeoapi). So is a missing `Accept-Post` with POST in Allow (`/req/create-replace-delete/options-accept-post`).
- OPTIONS on the items endpoint (POST) and on one item endpoint (PUT/PATCH/DELETE) are both needed. Item-level Allow may differ per feature (ownership-based rules), so a client can't generalize from one feature to all.

### Gaps
- I found no public server that demonstrably returns a *different* `Allow` per authenticated user apart from CubeWerx's own claim. No independent verification.
- Whether HEAD/GET-only Allow on a non-editable collection versus a 404/405 to OPTIONS is the common behaviour across GeoServer, QGIS Server and others was not surveyed here.

## 4. CORS preflight: Access-Control-Allow-Methods versus authorization; browser constraints

### Takeaway
`Access-Control-Allow-Methods` only states which methods the server lets *cross-origin scripts* use. It is computed for a credential-less request, so it can't express per-user authorization. The browser-generated preflight is invisible to script. A script that wants a credentialed `Allow` must issue its own OPTIONS, which cross-origin triggers a second, browser-generated preflight. To read `Allow` it then needs `Access-Control-Expose-Headers: Allow`, an echoed origin and `Access-Control-Allow-Credentials: true`. Part 4's new informative text about "a single OPTIONS" for both purposes doesn't hold for credentialed browser clients.

### Cited Findings
- Fetch: "`Access-Control-Allow-Methods` Indicates which methods are supported by the response's URL for the purposes of the CORS protocol. The `Allow` header is not relevant for the purposes of the CORS protocol." — [Fetch §3.3.3](https://fetch.spec.whatwg.org/#http-responses)
- Fetch: "Note that even so, a CORS-preflight request never includes credentials." — [Fetch §3.3.5](https://fetch.spec.whatwg.org/#cors-protocol-and-credentials)
- Fetch: for `Access-Control-Expose-Headers`, `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers`, "the value `*` counts as a wildcard for requests without credentials." — [Fetch §3.3.4](https://fetch.spec.whatwg.org/#http-new-header-syntax)
- Fetch preflight check: "If request's method is not in methods, request's method is not a CORS-safelisted method, and request's credentials mode is 'include' or methods does not contain `*`, then return a network error." CORS-safelisted methods are only "GET, HEAD, or POST". — [Fetch §4.8](https://fetch.spec.whatwg.org/#cors-preflight-fetch), [§2.2.1](https://fetch.spec.whatwg.org/#methods)
- Fetch: "A CORS non-wildcard request-header name is a header name that is a byte-case-insensitive match for `Authorization`." `Access-Control-Allow-Headers: *` does not cover Authorization, which must be listed explicitly. — [Fetch §2.2.2](https://fetch.spec.whatwg.org/#terminology-headers)
- Fetch: `Access-Control-Request-Method` and `Access-Control-Request-Headers` are forbidden request headers, so script can't forge a preflight. The CORS-safelisted response headers are Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified and Pragma. `Allow` and `WWW-Authenticate` are not among them and need `Access-Control-Expose-Headers` on the actual response. — [Fetch §2.2.2](https://fetch.spec.whatwg.org/#terminology-headers), [§2.2.6](https://fetch.spec.whatwg.org/#responses)
- Fetch: `Access-Control-Max-Age` "Indicates the number of seconds (5 by default) the information provided by the `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` headers can be cached." A preflight may respond 403 "coupled with omitting the relevant headers". Responses "can differ between the response to the CORS-preflight request and the CORS request that follows it". — [Fetch §3.3.3](https://fetch.spec.whatwg.org/#http-responses)
- Part 4 draft.3 (PR #1076, merged 2026-09-02, closes #1005): "General HTTP discovery and cross-origin requests can be combined into a single HTTP OPTIONS request that includes the standard CORS preflight request headers (`Origin` and `Access-Control-Request-Method`) ... returning the `Access-Control-Allow-Origin` and `Access-Control-Allow-Methods` headers, and simultaneously ... the standard `Allow` response header". The accompanying note: "Servers may need to use the `Access-Control-Expose-Headers` response header ... (e.g. `Access-Control-Expose-Headers: Allow`)." — [clause_6 "Cross-origin requests"](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_6_create-replace-delete.adoc), [PR #1076](https://github.com/opengeospatial/ogcapi-features/pull/1076)
- In #1005, m-mohr quoted the Fetch rule that preflights never include credentials and asked whether "two OPTIONS request from a web app" would result. pvretano replied that "one OPTIONS request should handle it". After implementing it, m-mohr found: "APIs must send Access-Control-Expose-Headers: Allow or the browser hides the Allow header". — [ogcapi-features#1005](https://github.com/opengeospatial/ogcapi-features/issues/1005)
- ldproxy answers every OPTIONS (preflight or script-issued) with `Access-Control-Allow-Origin: *` and no `Access-Control-Allow-Credentials`. Its code comment says "a browser rejects a credentialed cross-origin request whose preflight allows any origin". It sends no `Access-Control-Expose-Headers`. — [ldproxy OptionsEndpoint.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-stable/ogcapi-foundation/src/main/java/de/ii/ogcapi/foundation/infra/rest/OptionsEndpoint.java)
- pygeoapi's optional CORS uses `CORS(APP, expose_headers='*')`. — [pygeoapi flask_app.py ~L85-89](https://github.com/geopython/pygeoapi/blob/master/pygeoapi/flask_app.py)

### Inferences
- **Cross-origin, credentialed (Basic/Bearer/cookie) discovery from a browser works only like this:**
  1. Script calls `fetch(url, {method: 'OPTIONS', credentials: 'include'})` and/or sets `headers: {Authorization: ...}`.
  2. OPTIONS is not a safelisted method, so the browser first sends its own preflight. That preflight is credential-less and carries `Access-Control-Request-Method: OPTIONS` (plus `Access-Control-Request-Headers: authorization` if set).
  3. The preflight must answer 2xx with `Access-Control-Allow-Methods` explicitly containing `OPTIONS` (no `*` if credentials mode is include), `Access-Control-Allow-Headers` explicitly containing `Authorization`, and an echoed `Access-Control-Allow-Origin`. When credentials mode is include it also needs `Access-Control-Allow-Credentials: true`.
  4. The actual OPTIONS response must again carry ACAO, ACAC when credentialed, and `Access-Control-Expose-Headers: Allow, Accept-Post, Accept-Patch` (no `*` when credentialed).

  If any of this is missing, the client sees a network error or a hidden `Allow`. That is a server CORS-configuration inconsistency the library should report, not work around. This follows from the cited Fetch rules.
- The PR #1076 text describes a server responding once to a preflight. A browser script can never observe that preflight response and can't set `Access-Control-Request-Method`. Its "single round-trip" holds only for non-browser clients, and the preflight is always credential-less, so its `Allow` is the anonymous view. This is worth flagging as a spec-text weakness, because it contradicts Req 16C's "context of the request" for authenticated users.
- With pygeoapi's `expose_headers='*'`, `Allow` becomes readable for *non*-credentialed requests only, per Fetch §3.3.4. With ldproxy's `ACAO: *` and no ACAC, credentialed cross-origin OPTIONS fails entirely. Script can still read `Allow` without credentials only if exposed, which ldproxy doesn't do, but its text/plain body lists the methods and *is* readable for non-credentialed requests. Non-credentialed results are, by definition, not per-user.
- `Access-Control-Allow-Methods` should never be interpreted as authorization. Servers often send a static superset such as `GET, POST, PUT, PATCH, DELETE, OPTIONS` for every path.
- Same-origin deployments (client served from the API origin, or via a reverse proxy) avoid all of this: no preflight, all headers readable, cookies/Basic sent automatically.
- A 401 with `WWW-Authenticate: Basic` on a same-origin or credentialed request can trigger the browser's native login dialog. `WWW-Authenticate` is readable cross-origin only if exposed.

### Gaps
- Behaviour of the native Basic-auth dialog for fetch() 401 responses differs by browser. No normative source was checked here.
- I didn't find a test of how many public OGC API servers expose `Allow` via `Access-Control-Expose-Headers`.

## 5. Status codes as signals and "safe probe" ideas

### Takeaway
401, 403, 405, 501 and 404 have clear RFC 9110 meanings, and Part 4 lists them (as "strongly encouraged", not mandatory). They are only reliably obtained *by attempting the operation*. Every proposed "safe probe" (bogus If-Match, DELETE of a non-existent id, invalid POST body) depends on server-specific ordering of authentication, authorization, existence, validation and precondition checks. It can be destructive when a server ignores the precondition. Servers may also deliberately mask 403 as 401 or 404. No standardized safe write probe exists; OPTIONS is the standardized non-destructive probe.

### Cited Findings
- Part 4 Table "Typical HTTP status codes": 401 "requires user authentication. The response includes a `WWW-Authenticate` header"; 403 "authentication is not the issue, but the client is not authorized to perform the requested operation on the resource"; 405 "The request method is not supported"; 202 "might or might not eventually be acted upon, as it might be disallowed when processing happens". Only 200/201/202/204/404 are mandated; the rest are "strongly encouraged". "API clients should be prepared to handle any registered HTTP or HTTPS status code." — [clause_6 (draft.3)](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_6_create-replace-delete.adoc)
- Part 4 Security Considerations: "for security reasons, the server may also decide to return other status codes to hide information ... the server may decide to return a 401 response even for a valid, but un-privileged user. Or the server may return a 404 response". — [clause_13 (draft.3)](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_13_security_considerations.adoc)
- RFC 9110 §15.5.2: a 401 "MUST send a WWW-Authenticate header field ... If the request included authentication credentials, then the 401 response indicates that authorization has been refused for those credentials." §15.5.4: 403 "If authentication credentials were provided ... the server considers them insufficient ... However, a request might be forbidden for reasons unrelated to the credentials. An origin server that wishes to 'hide' the current existence of a forbidden target resource MAY instead respond with ... 404". §15.5.6: 405 "The origin server MUST generate an Allow header field in a 405 response containing a list of the target resource's currently supported methods." §10.2.1: "An empty Allow field value indicates that the resource allows no methods". §15.6.2: 501 "is the appropriate response when the server does not recognize the request method and is not capable of supporting it for any resource." — [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-status-codes)
- RFC 9110 §13.2.1: preconditions are evaluated "after it has successfully performed its normal request checks and just before it would ... perform the action"; "A server MUST ignore all received preconditions if its response to the same request without those conditions ... would have been a status code other than a 2xx ... or 412". §13.2.2: if If-Match is false, "respond 412 ... unless it can be determined that the state-changing request has already succeeded". §13.1.1: "the origin server MUST evaluate the If-Match condition per Section 13.2 prior to performing the method." — [RFC 9110 §13](https://www.rfc-editor.org/rfc/rfc9110.html#name-evaluation)
- Part 4 `/req/create-replace-delete/put-rid-exception`: A, 404 if the target doesn't exist and PUT-create is unsupported; B, 412 if PUT-create is supported, If-Match is present and the resource doesn't exist. The NOTE says per RFC 9110 §13.2.1 the 404 failure takes precedence over the precondition. — [replace/REQ_rid-exception.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/create-replace-delete/replace/REQ_rid-exception.adoc)
- `/rec/delete/no-feature`: deleting a non-existent id "SHOULD be `404`" (draft.2 Rec 1). Only a recommendation. — [Part 4 draft.2](https://docs.ogc.org/DRAFTS/20-002r1.html)
- ETag/If-Match evaluation is required only for servers in the Optimistic Locking using ETags class (`/req/optimistic-locking-etags/ifmatch-put-eval` and similar). — [requirements/optimistic-locking-etags](https://github.com/opengeospatial/ogcapi-features/tree/master/extensions/transactions/create-replace-update-delete/standard/requirements/optimistic-locking-etags)
- pygeoapi answers a mutation on a non-editable collection with **400** `InvalidParameterValue` "Collection is not editable", not 405 with Allow. — [pygeoapi itemtypes.py ~L789-793](https://github.com/geopython/pygeoapi/blob/master/pygeoapi/api/itemtypes.py)
- ldproxy authorization order: if the operation is in the `public` group, access is granted "even if no token or an invalid token were provided". Otherwise there are token, audience, scope, permission and policy (PDP) checks. — [ldproxy ApiSecurity.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-stable/ogcapi-foundation/src/main/java/de/ii/ogcapi/foundation/domain/ApiSecurity.java)
- RFC 6750 bearer error semantics (400/401/403, `error="invalid_token"`, `insufficient_scope`) were recommended in an OGC discussion. The SWG position: "Authentication protocols are defined in standards outside of our direct control. So they are out of scope". — [ogcapi-common#183](https://github.com/opengeospatial/ogcapi-common/issues/183)

### Inferences (honest risk assessment of probes)
- **PUT/PATCH/DELETE with `If-Match: "<bogus>"` on an existing feature, expecting 412.** This is safe only if the server implements ETag evaluation (conformance `optimistic-locking-etags`) and any proxy in front preserves the header. A server that ignores If-Match performs the replace or delete, which **destroys data**. Even a conformant server orders checks so that 401/403 precede 412 (RFC 9110 §13.2.1), so 412 does imply "authorized". 401/403 implies "not authorized" only if the server doesn't mask. Verdict: usable *only* when the ETags conformance class is declared *and* a prior GET returned an `ETag`. It is still a risk that can't be eliminated; never default-on.
- **DELETE or PUT on a guaranteed-non-existent id, expecting 404 versus 403/401.** Outcome depends on whether the server checks existence before authorization. Both orders are legal, and RFC 9110 lets a server return 404 to hide. A 404 is ambiguous ("authorized but missing" or "masked"). PUT on a non-existent id may *create* a feature when `supportsNonAutogeneratedResourceIds` is true. Verdict: unreliable, and PUT is dangerous.
- **POST with an intentionally invalid body, expecting 400/422 versus 401/403.** Validation-before-authorization yields 400 for everyone. A body that the server leniently accepts creates a feature (Part 4 has lenient-handling permissions). A 202 response doesn't even mean authorized, because "it might be disallowed when processing happens". Verdict: unreliable and potentially side-effecting.
- **405 with Allow** is the only status that, by RFC 9110 MUST, carries machine-readable method information. Getting it requires sending the unsafe method. It also tells "not supported for the resource", not "not authorized". Some servers return 400 (pygeoapi) or 403 instead. Verdict: useful for *post-hoc* classification after a real user-initiated write, not for probing.
- **401 versus 403 interpretation.** 401 means "(re)authenticate", and the `WWW-Authenticate` challenge reveals the schemes (Basic realm, Bearer `error=...`). 403 means "authenticated but not permitted (or not permitted at all)". Servers may send 401 for unprivileged users. The practical client approach is to let the user attempt the edit and classify the failure, not to predict it.
- **501** means the method is unknown server-wide. That is a strong "server can't do this method" signal, but it is again obtained only by sending the method.

### Gaps
- No survey of real servers' check ordering (auth versus existence versus validation) was found.
- No OGC text endorses or forbids probing.

## 6. Collection metadata, links and schema signals of editability

### Takeaway
Part 4 defines exactly one collection-metadata property related to writes: `supportsNonAutogeneratedResourceIds`. It signals PUT-create, not editability or permission. Schema `readOnly` (via Part 5 receivables) marks *properties* that can't be set. No standard link relation or `x-ogc` member advertises "this collection is editable" or "editable by you". Per-collection editability is server configuration (pygeoapi `editable`, ldproxy provider `mutations`) and is not exposed in collection JSON.

### Cited Findings
- `/req/features/collection-endpoint` A: "If the server supports creating new features for a collection `collectionId` using the PUT method, the server SHALL include a boolean property `supportsNonAutogeneratedResourceIds` with the value `true` in the representation of the collection at the endpoints `{landingPageUri}/collections` and `{landingPageUri}/collections/{collectionsId}`." — [features/REQ_collection-endpoint.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/features/REQ_collection-endpoint.adoc)
- `/req/features/schema` (condition: Part 5 "Returnables and Receivables"): /collections/{id}/schema is JSON Schema; the server accepts receivable properties; with `"additionalProperties": false` it rejects unknown properties; E: "The server SHALL reject mutation requests that set a property which is specified in the JSON Schema with a statement `"readOnly": true`." — [features/REQ_schema.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/features/REQ_schema.adoc)
- ldproxy documents that receivables are "the schema of the collection excluding properties marked as `readOnly`", and offers a profile `all-as-receivable` for fetching an editable representation. — [ldproxy CrudBuildingBlock.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-draft/ogcapi-crud/src/main/java/de/ii/ogcapi/crud/app/CrudBuildingBlock.java)
- ldproxy enables CRUD per collection only if the feature provider's `mutations` capability is supported (`FeatureProvider::mutations ... isSupported`). This is internal and not emitted in collection metadata as far as the sources show. — [EndpointCrud.java](https://github.com/interactive-instruments/ldproxy/blob/master/ogcapi-draft/ogcapi-crud/src/main/java/de/ii/ogcapi/crud/app/EndpointCrud.java)
- pygeoapi: per-collection `editable: true` in the provider configuration. "Authentication and authorization are outside pygeoapi's scope." — [pygeoapi transactions docs](https://docs.pygeoapi.io/en/latest/transactions.html), [itemtypes.py](https://github.com/geopython/pygeoapi/blob/master/pygeoapi/api/itemtypes.py)
- An early SWG idea (2021) was a flag in collection metadata, but "there were concerns expressed about an ever expanding metadata blob at the /collections or /collections/{collectionId} endpoints", so OPTIONS was preferred. — [ogcapi-features#505](https://github.com/opengeospatial/ogcapi-features/issues/505)
- #1005 listed "Add a transaction link to the item/collection only when the user has permission" and "a transactions flag to the landing page" as options. Neither was adopted; the resolution was OPTIONS plus CORS text. — [ogcapi-features#1005](https://github.com/opengeospatial/ogcapi-features/issues/1005)
- IANA link relations `edit` (RFC 5023), `edit-form` and `create-form` (RFC 6861) exist in the registry but are not used by any OGC API Features part found here. — [IANA Link Relations](https://www.iana.org/assignments/link-relations/link-relations.xhtml)

### Inferences
- `supportsNonAutogeneratedResourceIds: true` implies the collection is mutable via PUT for *someone*. Its absence implies nothing about POST/PATCH/DELETE.
- A schema with every property `readOnly` would effectively signal "no receivable properties". That is a heuristic, not a Part 4 rule.
- Any `edit`/`create-form` links, vendor `x-...` flags or STAC-style link `method` members are vendor heuristics. A client may *display* them but should cross-check with OPTIONS.

### Gaps
- GeoServer's, QGIS Server's and Esri's OGC API Features collection JSON were not inspected for vendor editability flags here.
- The Part 5 (Schemas) final URIs and `x-ogc-role` interplay with receivables were not checked.

## 7. OGC proposals and GitHub issues on advertising permissions per user

### Takeaway
The question has been raised repeatedly since 2019, in #10, #135, common#179, common#159, common#183, #505, #1005 and #1058. The SWG's consistent answer is that auth mechanisms are out of scope, HTTP OPTIONS/Allow (optionally with link hints in the body) is the discovery mechanism, and the API definition "must reflect" per-user methods informatively. No per-user permissions document, conformance variation or collection flag has been standardized.

## 8. Analogous systems and lessons

### Takeaway
Older OGC and other ecosystems show the same tension. Static, service-level capability lists (WFS 2.0 `ImplementsTransactionalWFS`, Esri `capabilities`, OData `InsertRestrictions`) describe configuration, not the current user's rights. Only WebDAV ACL (`DAV:current-user-privilege-set`) defines a true per-user privilege query. WFS even *removed* per-feature-type operations between 1.1 and 2.0.

### Cited Findings
- WFS 1.1.0 `FeatureTypeType` has an `Operations` element with values `Insert, Update, Delete, Query, Lock, GetGmlObject` per feature type. In the WFS 2.0 schema, `FeatureTypeType` (Name, Title, Abstract, Keywords, DefaultCRS, OtherCRS, NoCRS, OutputFormats, WGS84BoundingBox, MetadataURL, ExtendedDescription) has **no** `Operations` element. — [WFS 1.1.0 wfs.xsd](https://schemas.opengis.net/wfs/1.1.0/wfs.xsd), [WFS 2.0 wfs.xsd](https://schemas.opengis.net/wfs/2.0/wfs.xsd)
- WFS 2.0 service constraints: "ImplementsTransactionalWFS ... Indicates that the server implements the Transactional WFS conformance class", and `ImplementsLockingWFS`. These are server-wide booleans in OperationsMetadata. — [OGC 09-025r2 WFS 2.0.2](https://docs.ogc.org/is/09-025r2/09-025r2.html)
- Esri feature service `capabilities` string includes Create, Delete, Query, Update, Editing, Uploads, Sync, Extract and others. "Editing" requires Create, Delete and Update plus `allowGeometryUpdates`. `editorTrackingInfo` holds `enableOwnershipAccessControl`, `allowOthersToUpdate` and `allowOthersToDelete`. — [ArcGIS REST Feature Service](https://developers.arcgis.com/rest/services-reference/enterprise/feature-service/)
- Esri: "The layer owner, organization administrators, and members of shared update groups ... can edit a hosted feature layer ... even when editing is not enabled on the layer." So advertised capabilities are not the user's effective rights. — [ArcGIS Online: Manage hosted feature layer editing](https://doc.arcgis.com/en/arcgis-online/manage-data/manage-editing-hfl.htm)
- OData Capabilities vocabulary: `InsertRestrictions/Insertable` ("Entities can be inserted"), `UpdateRestrictions/Updatable` and `DeleteRestrictions/Deletable`, each with `Permissions` ("Required permissions. One of the specified sets of scopes is required to perform the insert"). These are annotations on the static service metadata. — [Org.OData.Capabilities.V1](https://github.com/oasis-tcs/odata-vocabularies/blob/main/vocabularies/Org.OData.Capabilities.V1.md)
- WebDAV ACL RFC 3744 §5.4: "DAV:current-user-privilege-set is a protected property containing the exact set of privileges (as computed by the server) granted to the currently authenticated HTTP user ... A user-agent can use the value of this property to adjust its user interface ... (e.g., by graying out a menu item or button) ... without having to actually execute an operation." — [RFC 3744](https://www.rfc-editor.org/rfc/rfc3744.html#section-5.4)
- STAC Authentication Extension, discussed as an alternative: it is link-based auth metadata, primarily for assets. — [stac-api-extensions/transaction#15](https://github.com/stac-api-extensions/transaction/issues/15)

### Inferences
- Lesson 1: service-level flags (WFS 2.0 constraint, OGC conformance, Esri `capabilities`, OData `Insertable`) answer "can this service ever write", not "can I write now". Esri's owner/admin bypass shows the two can disagree in both directions.
- Lesson 2: the only design built for UI enablement (greying out buttons) is a per-user, server-computed privilege set (WebDAV). In OGC API the closest equivalent is a context-sensitive `Allow` per Req 16C, which servers rarely implement per user today.
- Lesson 3: OData's `Permissions` (required scopes) and OpenAPI `security` both state *requirements*, leaving the user-to-scope match to the client. They only work if the client can inspect its token's scopes. That is possible for some JWTs but not for opaque tokens, Basic or cookies.

### Gaps
- JSON:API was not researched in depth. I found no evidence it defines a permissions or capabilities member (its `meta` is free-form), but this wasn't verified against jsonapi.org.
- GeoServer's per-user GetCapabilities filtering ("hide" or "challenge" catalog modes) and whether write rules affect WFS-T capabilities could not be confirmed. The docs page fetched didn't yield usable text.

## 9. Consolidated catalogue: mechanisms ranked by granularity and reliability (for a browser TypeScript client)

### Takeaway
No standardized mechanism guarantees, before the write, that *this user* may write *this* collection. The best layered approach is:
1. Conformance, for a server-level gate.
2. OpenAPI, optionally, for configuration-level per-path methods.
3. Credentialed OPTIONS/Allow per items and item endpoint, for the standardized per-resource and (ideally) per-user answer.
4. The actual write's 401/403/405 result as the only authoritative answer, classified and reported.

### Cited Findings
- Per-resource, per-request-context: OPTIONS `Allow`. This is normative (Req `/req/create-replace-delete/options-response` C). — [REQ_response.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/create-replace-delete/options/REQ_response.adoc)
- Per-path by configuration, possibly per-user: OpenAPI paths and methods, informatively required to "reflect" privileges. — [clause_13 (draft.3)](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_13_security_considerations.adoc)
- Server-wide: conformance classes. — [clause_2_conformance.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_2_conformance.adoc)
- Per-collection, narrow: `supportsNonAutogeneratedResourceIds` (PUT-create only). — [REQ_collection-endpoint.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/features/REQ_collection-endpoint.adoc)
- Per-property: JSON Schema `readOnly` (Part 5 receivables). — [REQ_schema.adoc](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/requirements/features/REQ_schema.adoc)
- Post-hoc: 401 + `WWW-Authenticate`, 403, 405 + `Allow` (MUST), 501, 404 (possibly masked). — [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-status-codes), [clause_13 (draft.3)](https://github.com/opengeospatial/ogcapi-features/blob/master/extensions/transactions/create-replace-update-delete/standard/clause_13_security_considerations.adoc)
- Not authorization: `Access-Control-Allow-Methods`. — [Fetch §3.3.3](https://fetch.spec.whatwg.org/#http-responses)

### Inferences
Summary table:

| Mechanism | Standardized? | Granularity | Per-user in practice | Browser cross-origin readable | Side effects |
|---|---|---|---|---|---|
| /conformance Part 4 URIs | Yes (draft) | server | No (spec silent; pygeoapi/ldproxy static) | Yes (GET) | None |
| OpenAPI paths/methods | Partly (Part 1 `oas-impl`; Part 4 informative) | per path, or generic `{collectionId}` | Sometimes (CubeWerx claims) | Yes (GET) | None; heavy |
| OpenAPI `security` | OpenAPI | per operation | No: auth requirement only | Yes | None |
| OPTIONS `Allow` (+`Accept-Post`/`Accept-Patch`) | Yes (Part 4 Req 1B, 15, 16) | per resource | Intended (Req 16C, #1058); ldproxy/pygeoapi config-only | Only with `Expose-Headers: Allow`; with credentials also explicit ACAO + ACAC + `OPTIONS` in Allow-Methods + `Authorization` in Allow-Headers | None (safe method) |
| OPTIONS body link hints | Informative (draft.3) | per resource | Possible | Body readable if CORS OK | None |
| `supportsNonAutogeneratedResourceIds` | Yes (draft) | per collection | No | Yes | None |
| Schema `readOnly` | Yes (Part 4 + Part 5) | per property | No | Yes | None |
| `Access-Control-Allow-Methods` | Fetch | per URL, credential-less | Never | Not readable by script | None |
| 401/403/405/501 from real write | RFC 9110 | per request | Yes (authoritative, maskable) | Status yes; headers need expose | **The write itself** |
| If-Match bogus / DELETE-nonexistent / invalid POST probes | No | per request | Ambiguous | — | **Risk of data loss/creation** |

- Inconsistencies a reporting client can detect and surface without working around them:
  - CRD conformance declared but no endpoint advertises a write method.
  - `update` declared but PATCH absent from Allow.
  - POST in Allow without `Accept-Post`.
  - 405 without `Allow`.
  - 401 without `WWW-Authenticate`.
  - Allow not exposed cross-origin.
  - `ACAO: *` on credentialed endpoints.
  - 400 instead of 405/403 for a non-editable collection.
  - OpenAPI listing methods that OPTIONS doesn't, or the reverse.
  - Draft.2 `/req/` versus `/conf/` URI mix.

### Gaps
- No interoperability survey (e.g. OGC Testbed or Code Sprint report, 2025-2026) on per-user `Allow` was found.
- I couldn't determine whether the approved Part 4 will make per-user `Allow` normative (#1058 open).
